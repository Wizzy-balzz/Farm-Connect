Text: INTRODUCTION
--------------------------------------------------
[38] Style: Normal | Align: JUSTIFY (3)
Text: In the modern business environment, the efficient management of store operations plays a vital role in ensuring the smooth functioning of manufacturing and trading organizations. Handling procurement, inventory, material movement, and billing through manual or paper-based methods is time-consuming, error-prone, and lacks transparency. There is an urgent need for a reliable, digital solution that brings all these operations under one unified platform.
--------------------------------------------------
[39] Style: Normal | Align: JUSTIFY (3)
Text: The Store Management System is a comprehensive, full-stack web application designed to digitize and automate the complete lifecycle of store operations from raising purchase orders to issuing materials to departments. The system was developed to meet the real-world operational requirements of KR Exports, a trading and export organization, and is deployed in a live production environment.
--------------------------------------------------
[40] Style: Normal | Align: JUSTIFY (3)
Text: The application is organized into three major functional domains: Master Data Management, which covers all foundational records such as items, suppliers, departments, and stores; Transaction Management, which handles day-to-day operations including purchase orders, gate inwards, receipts, bill entries, item issues, and gate passes; and Reports & Analytics, which provides management with real-time visibility into all store activities through dynamic, exportable reports.
--------------------------------------------------
[41] Style: Normal | Align: JUSTIFY (3)
Text: The system is hosted at https://krexports.org and is supported by a Jenkins-based CI/CD pipeline for automated builds and deployments, making it production-ready and maintainable. This report documents the design, development, and implementation of the Store Management System, providing a complete technical overview of its architecture, features, and functionality.

--------------------------------------------------
[58] Style: Normal | Align: JUSTIFY (3)
Text: This module maintains centralized master records, including departments, suppliers, stores, items, product heads and sub-heads, units of measure (UOM), parties, purchase types, and states. These records ensure consistency and accuracy across all store transactions.
--------------------------------------------------

--------------------------------------------------
[60] Style: Normal | Align: JUSTIFY (3)

--------------------------------------------------
[62] Style: Normal | Align: JUSTIFY (3)

--------------------------------------------------
[64] Style: Normal | Align: JUSTIFY (3)
Text: The system uses bcrypt for password hashing and JSON Web Token (JWT) authentication to secure user access. Protected API routes, Axios response interceptors, and request rate limiting help prevent unauthorized access and manage invalid or expired sessions.
--------------------------------------------------

The modular architecture supports maintainability, scalability, and future enhancements.

Text: 8.0 Design Approach
--------------------------------------------------
[154] Style: Normal | Align: JUSTIFY (3)
Text: Each module of the Store Management System is described here the way a system design problem is solved: by walking through the same seven steps in the same order, every time. This keeps the explanation of every module complete and comparable, and shows why each design decision was taken rather than only what the screen looks like.
--------------------------------------------------
[156] Style: Heading 3 | Align: None
Text: Shared baseline for all modules
--------------------------------------------------
[157] Style: Normal | Align: JUSTIFY (3)
Text: Non-functional baseline. Every request travels through Helmet (HTTP hardening), CORS, a payload size limit, a rate limiter and the JWT authentication middleware before it reaches a controller. All data lives in a single MySQL database, so the system chooses consistency over availability in CAP terms (CP): a user may briefly be unable to save if the database is unreachable, but two users can never see conflicting versions of a purchase order or a stock balance. Money columns use DECIMAL, never floating point, so totals reconcile exactly.
--------------------------------------------------
[158] Style: Normal | Align: JUSTIFY (3)
Text: Sizing baseline (assumptions).
--------------------------------------------------
[160] Style: Normal | Align: JUSTIFY (3)
Text: A single Node.js process and one MySQL instance handle this load comfortably. The design keeps the application stateless (JWT instead of server sessions), so extra Node.js instances can be added behind a load balancer if usage grows.

Text: 8.2.0 Purpose & Scope
--------------------------------------------------
[189] Style: Normal | Align: JUSTIFY (3)
Text: Provides tokenized authentication, secure credential management, and Role-Based Access Control (RBAC) across the enterprise, preventing unauthorized data modifications.
--------------------------------------------------
[190] Style: Heading 3 | Align: None
Text: 8.2.1 Functional Requirements
--------------------------------------------------
[191] Style: Normal | Align: JUSTIFY (3)
Text: What the module must do:
--------------------------------------------------
[192] Style: List Paragraph | Align: JUSTIFY (3)
Text: A user signs in with a username and password and receives a signed JWT plus a profile (id, full_name, role).
--------------------------------------------------
[193] Style: List Paragraph | Align: JUSTIFY (3)
Text: A signed-in user can change their own password; administrators can register new users.
--------------------------------------------------
[194] Style: List Paragraph | Align: JUSTIFY (3)
Text: Four roles – admin, manager, operator, viewer – decide which endpoints a user may call.
--------------------------------------------------
[195] Style: List Paragraph | Align: JUSTIFY (3)
Text: Each account has an active / inactive status so access can be withdrawn without deleting the record, and the last login time is stored.
--------------------------------------------------
[196] Style: List Paragraph | Align: JUSTIFY (3)
Text: The browser redirects unauthenticated users to the login screen (protected routes) and handles an expired or invalid token centrally.
--------------------------------------------------
[197] Style: Normal | Align: JUSTIFY (3)
Text: Out of scope: self-service sign-up, social login / SSO and multi-factor authentication.
--------------------------------------------------
[198] Style: Heading 3 | Align: None
Text: 8.2.2 Non-Functional Requirements
--------------------------------------------------
[199] Style: Normal | Align: JUSTIFY (3)
Text: How well the module must do it (the system-wide baseline in the chapter introduction also applies):
--------------------------------------------------
[200] Style: List Paragraph | Align: JUSTIFY (3)
Text: Security: passwords are stored only as bcryptjs hashes with auto-generated salts; the hash is never returned by the API.
--------------------------------------------------
[201] Style: List Paragraph | Align: JUSTIFY (3)
Text: Brute-force defence: at most 15 login attempts per 15 minutes per IP address on /api/auth/login.
--------------------------------------------------
[202] Style: List Paragraph | Align: JUSTIFY (3)
Text: Session length: tokens expire after 12 hours, which limits the damage of a stolen token while avoiding repeated logins in one shift.
--------------------------------------------------
[203] Style: List Paragraph | Align: JUSTIFY (3)
Text: Scalability: because tokens are stateless, any server instance can validate a request without a shared session store.
--------------------------------------------------
[204] Style: List Paragraph | Align: JUSTIFY (3)
Text: Latency target: login under 500 ms (dominated by the deliberate cost of bcrypt); token verification adds only microseconds per request.
--------------------------------------------------
[205] Style: List Paragraph | Align: JUSTIFY (3)
Text: CAP: the user table is a single MySQL source of truth – consistency is preferred, so a disabled account is refused immediately on the next login.
--------------------------------------------------

[216] Style: List Paragraph | Align: JUSTIFY (3)

[220] Style: List Paragraph | Align: JUSTIFY (3)

[577] Style: Heading 1 | Align: CENTER (1)
Text: CONCLUSION
--------------------------------------------------
[578] Style: Normal | Align: JUSTIFY (3)
Text: The Store Management System provides a complete digital solution for managing the major activities involved in store and inventory operations. The system integrates master data management, purchase orders, gate inward entries, goods receipts, bill processing, item issues, gate passes, dashboards, and reports within a single application. By replacing manual records and disconnected processes, it improves the accuracy, consistency, and accessibility of operational information. The application was developed using React for the frontend, Node.js and Express for the backend, and MySQL with Sequelize for database management. Its client-server architecture supports structured communication between the user interface, application server, and database. JWT authentication, password hashing, role-based access control, request rate limiting, and protected routes help secure the system and prevent unauthorized access. The completed project demonstrates how a web-based information system can simplify store operations, reduce repetitive work, minimize recording errors, and improve decision-making. Its modular structure makes the application easier to maintain and allows additional features to be introduced in the future. Overall, the Store Management System successfully meets its objective of providing a secure, organized, and efficient platform for managing store activities at KR Exports.
